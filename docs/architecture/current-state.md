## Accurate description

Iroko is a **typed, local-first conversational runtime with persistent legacy
memory and on-demand visual adapters**. It is more than `STT -> LLM -> TTS`,
but it is not yet a situated multimodal cognitive system.

```text
audio, text, or one requested frame
                |
                v
      channel adapter / request scope
                |
                v
unknown ActivePersonContext by default
 (face / face+voice / PIN resolve an actor for protected branches; a generic turn
  names its speaker by face and an observed token, never by voice, and never spends a grant)
                |
      identified speaker -> one in-process short-term session (3000 characters, 180 s of silence)
      unknown or ambiguous speaker -> session suspended: nothing read, nothing written
      no MANUAL evidence -> no retrieval or legacy durable memory (every turn today)
      face-identified voice turn + MEMORY_CANDIDATES_ENABLED (default off) -> background candidate
        proposal after the reply: voice check, gate, extractor, classifier, policy, candidate store
        and, while a candidate waits, an offer prepared beside generation (voice check of the
        turn's clip) and spoken after the reply; an answer-shaped message resolves the actor
        (face and voice) first, then promotes or rejects
                |
                v
P0 controller adapters (`/chat`, classic `/transcribe`, streaming audio, and visual dialogue)
  |-- deterministic date/strict-ISO age
  |-- protected household, no identified owner -> unauthorized
  |-- identified owner: child list/count -> policy-gated v4 tools
  |-- identified owner: other household questions -> "not connected yet"
  `-- generic text -> legacy local text turn
                |
                v
response + local Piper + optional spoken memory offer + optional background candidate proposal (voice only)
```

`/transcribe/stream` and `/vision/respond` now create a fresh typed event and
ask the controller to decide before legacy generation. Safe plans never reach
the LLM, legacy memory, or a candidate proposal. Since Plan 0023 (P0-C7), the
controller's `decide()` can also return a `SceneDescriptionRequest`
capability instead of a closed plan; only `/vision/respond`'s scene branch
may fulfill it by reading a frame and calling the VLM, and that description
goes directly to Piper — never through the legacy text LLM. A generic
non-scene visual request delegates to legacy generation with no perception
at all. This does not establish face identity, authorization, or durable
visual memory.

The shared text path is `server/src/server/text_turn.py`. Since Plan 0061 (CM-2)
the routers name the speaker of a generic turn (`cognition/generic_identity.py`:
the fusion resolver with no audio and `peek_actor`) after the controller decided
the turn is generic, and `text_turn.py` opens the one session slot of
`memory/continuity.py` for an `IDENTIFIED` person with at least `basic` assurance.
An unknown, probable or ambiguous speaker suspends the session for that turn.
The conversation id labels an event and never selects history. Durable memory
reads stay behind the `MANUAL` gate, which no production route emits. Since
Plan 0062 (CM-3a) `record_text_turn` can also hand a successful voice turn, with
its face-identified actor, to a scheduler the voice routers build; the background
task that follows keeps a stored memory candidate and nothing else. Since Plan 0063
the same seam also prepares, beside generation, the spoken offer of a waiting
candidate, and the controller answers an explicit closed verb («sí, autorizo.», «no autorizo»; the value is optional since Plan 0066, and «acepto» and «sí, guárdala» also answer since Plan 0067) (see
the memory-candidates row below). `/chat` and `/vision/respond` never propose, offer
or answer.

## Deliberately absent or deferred

- a generic `ToolRegistry`; P0 uses closed typed tools and does not justify a
  registry or framework;
- public consent input, name grounding, or any route to protected v4 data other
  than the child list/count after a PIN token (`/chat`, voice) or face/voice
  evidence (voice channels); no protected value reaches a prompt or the LLM;
- speaker binding of the PIN grant (ADR-0015 decision 2): a grant is now bound to one named operation (Plan 0051), but it still proves the PIN, not the speaker (ADR-0008); Plan 0050's matrix pins that limit;
- diarization and a second enrolled speaker or face (PC-6);
- a reserved-data capability (`SECURITY`): the `strong` requirement exists in policy and is proven only by synthetic tests, because nothing reserved is stored or readable yet;
- liveness/anti-replay defense for face and voice evidence (Plans 0029, 0054): a
  photograph of the owner identifies at assurance `basic`, and a photograph plus a
  recording of the exact question would satisfy `strong` once a reserved capability
  exists; PC-4 measured this on real hardware (a phone-screen photo and video did not
  identify) but does not defend it — no plan closes it yet; real-camera calibration/acceptance closed 2026-09-01 as
  [Plan 0030](../plans/completed/0030-real-camera-face-acceptance.md);
- typed `SceneObservation`, `WorldState`, tracking, scene graph, and spatial
  memory;
- the rest of the cognitive memory lifecycle: reflection, correction, forgetting and
  reading a stored memory back (since Plans 0062 and 0063 a taste candidate can be stored,
  offered aloud and promoted on an explicit spoken answer, behind the default-off
  `MEMORY_CANDIDATES_ENABLED`; since Plan 0074 the profile card reads the owner's tastes and
  two name datums back behind `PROFILE_CARD_ENABLED`, and nothing else is read back, corrected
  or forgotten: CM-5b, CM-6);
- cloud escalation gateway, ROS2, motors, and physical actions.
