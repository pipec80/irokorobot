## Decision summary

The first real `just run-server` plus `just run-robot` acceptance run proved
that P0's policy foundation works, but it also exposed three runtime defects
that automated tests did not catch:

1. deterministic intent recognition does not generalize across ordinary
   Spanish or observed STT variants;
2. generic streaming can complete successfully with no audio when Ollama
   combines conflicting output contracts;
3. visual dialogue adds an unnecessary second LLM that can alter a grounded
   VLM observation and spends camera time on identity requests that P0 cannot
   resolve.

P0 remains open. These defects will be corrected as three bounded slices:

- **P0-C5:** typed intent resolution plus a supervised regression corpus;
- **P0-C6:** channel-owned LLM output contracts plus mandatory audible stream
  fallback;
- **P0-C7:** typed visual intent and grounded scene responses without a second
  LLM.

No slice implements P1 identity, biometrics, onboarding, WorldState, live
self-learning, or a family policy profile.

## Goals

- Keep protected-data classification fail-closed and authorization before
  retrieval.
- Recognize bounded, ordinary expressions by intent rather than adding an
  ever-growing list inside the controller.
- Turn confirmed STT misses into reviewed regression examples without
  permitting runtime self-modification.
- Guarantee that every successful streaming turn with a transcript produces
  at least one audible WAV event or becomes an explicit error.
- Keep personality content separate from channel output formatting.
- Preserve visible facts in scene responses and avoid an unnecessary second
  language-model transformation.
- Avoid a camera request for identity while P0 has no trusted visual identity
  capability.
- Preserve all current HTTP, WAV, NDJSON, server/robot, local-first, identity,
  authorization, and database boundaries.

## Non-goals

- Face or speaker recognition, verification, fusion, or enrollment.
- Owner bootstrap, trusted personal sessions, consent UI, or family onboarding.
- Live learning from conversations or automatic mutation of intent rules.
- Embedding, fuzzy, LLM, or cloud authorization classification.
- Structured scene graphs, tracking, WorldState, episodic visual memory, or
  continuous camera processing.
- A new dependency, model, database migration, endpoint, or breaking event
  schema.
- General STT model tuning beyond aligning the documented product-name prompt
  with Iroko.

## Alternatives considered

### 1. Add more literal phrases and strengthen prompts

This is the smallest diff, but repeats the failure mode already demonstrated
by C4. It also leaves streaming correctness dependent on a 3B model obeying
two contradictory instructions and leaves visual grounding dependent on a
second probabilistic rewrite. Rejected.

### 2. Typed deterministic resolution plus supervised examples

This is the selected P0 approach. A pure resolver returns a typed need and a
non-sensitive rule identifier. Runtime behavior remains fast, local,
auditable, and fail-closed. Real phrases become versioned tests only after
operator review. Streaming and vision receive deterministic postconditions
around their model boundaries.

### 3. Semantic embeddings or an LLM intent classifier

This could generalize further, but introduces thresholds, model availability,
latency, false positives, and a new security boundary before P0 has an
evaluation corpus. It may be evaluated after C5 produces measured examples;
it is not justified for this remediation.

## P0-C5 — Typed intent resolution

### Contract

Classification moves out of controller execution into a pure typed service:

```python
class IntentMatch(StrEnum):
    EXACT = "exact"
    SUPERVISED_STT_ALIAS = "supervised_stt_alias"
    NONE = "none"


class IntentResolution(BaseModel):
    need: InformationNeed
    match: IntentMatch
    rule_id: str | None


def resolve_information_need(message: str) -> IntentResolution: ...
```

`rule_id` is stable operational metadata such as `date.current.explicit`; it
must never contain the utterance, a name, or a protected value. A numeric
confidence is deliberately omitted because deterministic rules are not
calibrated probabilities.

The controller consumes the result and remains the only component that calls
policy, tools, memory, or generic generation. The resolver never identifies a
speaker, grants permission, reads SQLite, or calls a model.

### Resolution order

```text
explicit child tools
    -> protected household / birth / personal data
    -> supervised ambiguous STT aliases
    -> current date
    -> explicit age calculation
    -> relationship/profile
    -> generic conversation
```

Protected meaning outranks date and age. For example, `fecha de nacimiento de
mi hija` stays protected rather than becoming a date-tool request.

Unambiguous forms such as the observed `Me dice la fecha actual`, `dime la
fecha actual`, `en qué fecha estamos`, and `qué fecha es hoy` use
`get_current_date` with `llm=0ms`. Observed corruptions such as `qué día soy`
and `qué vía es hoy` request clarification with `llm=0ms`; they are not
silently corrected into a factual claim.

### Supervised learning boundary

Iroko does not learn intent rules directly from runtime speech. The loop is:

```text
literal STT observation
    -> local operator labels intended need
    -> reviewed corpus entry
    -> RED regression
    -> deterministic rule change
    -> GREEN plus real rerun
```

The tracked corpus contains only synthetic or explicitly approved phrases. It
must not contain family facts, biometric data, raw audio, or opaque session
tokens.

## P0-C6 — Reliable streaming output

### Contract ownership

Personality defines identity, style, and behavioral limits. It does not own a
universal transport format. The generation adapter selects exactly one output
contract:

- classic generation: the existing JSON response/emotion contract and Ollama
  schema;
- streaming generation: one `EMOTION:<emotion>` line followed by plain text.

The implementation plan must remove the current contradiction where the
character base prompt says `SIEMPRE JSON` and the streaming suffix later says
`sin JSON`. Dynamic character profiles must follow the same separation.

### Server postcondition

Every successful streaming completion follows this order:

```text
text_heard exactly once
    -> emotion exactly once
    -> one or more non-empty audio events
    -> done exactly once and last
```

`done` is the certificate of success and must never be emitted before at least
one audio event. A TTS or transport failure after HTTP headers may truncate the
stream; in that case the server cannot promise a valid audio/done suffix, and
the absence of `done` is an explicit client-visible failure rather than a
successful silent turn.

If the model emits an empty stream, a truncated tag, the observed hybrid
emotion-plus-JSON form, or any other invalid protocol before valid speech,
the server emits neutral emotion plus the configured audible fallback. It
does not speak metadata, braces, or raw model output, and it does not record or
consolidate the invalid turn.

If generation fails after one or more sentences were already spoken, the
existing audio remains valid, an audible fallback completes the turn, and the
partial response is not persisted as a successful memory.

Raw invalid model output must not be written to INFO/WARNING logs. Operational
logs may record a bounded reason, character count, audio-chunk count, and
timings.

### Robot defense

The robot logs the text associated with each `AudioEvent` before playback. A
`done` event before any audio is a `ServerError`. Any EOF without one final
`done` is also a `ServerError`, even when one or more audio chunks were already
played. Duplicate or out-of-order terminal events are rejected rather than
silently returning to idle.

The server measures request start to first `AudioEvent` ready. The robot
measures request start to first chunk received and playback start. Both log a
bounded failure reason and `None` when no first audio exists, plus the total
chunk count. This remediation does not require new public NDJSON fields; an
additive schema change may be proposed separately only if logs prove
insufficient.

## P0-C7 — Grounded visual dialogue

### Typed visual needs

The C7 slice extends the C5 resolver with three distinct needs:

- `SCENE_DESCRIPTION`: requires one current frame;
- `ACTIVE_IDENTITY`: cannot be answered from P0 evidence and returns a fixed
  unknown response;
- `BIOMETRIC_ENROLLMENT`: public spoken enrollment is unavailable and returns
  a fixed rejection without capturing a frame.

The controller produces an internal typed capability request for
`SCENE_DESCRIPTION`, distinct from a user-facing `ResponsePlan`. Channel
adapters must handle this union exhaustively. `ACTIVE_IDENTITY` produces the
deterministic response `Todavía no puedo confirmar quién sos.` and never
requests a frame, LLM, memory, or biometric adapter. `BIOMETRIC_ENROLLMENT`
uses the fixed spoken response `Todavía no puedo registrar rostros: hace falta
administración local y consentimiento.` and likewise never requests a frame.
A spoken name or face-learning phrase is not authorization or consent. This
spoken response is separate from the existing HTTP detail returned by the
administrative enrollment endpoint.

This internal contract is not a public API change. The classic robot flow
continues using the existing `vision_requested` response field and
`/vision/respond` round trip for a scene request.

### Channel behavior matrix

| Need/channel | `/transcribe` | `/transcribe/stream` | `/chat` | `/vision/respond` |
|---|---|---|---|---|
| Scene, vision enabled | Existing audible cue plus `vision_requested=true` | Fixed capability-unavailable response; streaming has no frame round trip | Fixed capability-unavailable response | Preflight, one VLM call, grounded audio |
| Scene, vision disabled | Fixed capability-unavailable response | Fixed capability-unavailable response | Fixed capability-unavailable response | Endpoint remains disabled/unavailable |
| Active identity | Fixed unknown; no frame | Fixed unknown; no frame | Fixed unknown | Fixed unknown before image/VLM work |
| Biometric enrollment | Fixed restricted/unavailable; no frame | Fixed restricted/unavailable; no frame | Fixed restricted/unavailable | Fixed restricted/unavailable before image/VLM work |
| Protected/deterministic | Existing `ResponsePlan`; no frame | Existing safe stream plan; no frame | Existing controller plan | Existing controller plan before image/VLM work |

Every adapter must exhaustively handle the internal decision. A capability
request must never fall through to generic LLM generation. Direct calls to
`/vision/respond` perform the same preflight before decoding or describing an
image. That non-visual preflight runs even when `VISION_ENABLED=false`, so
identity, enrollment, protected, and deterministic needs still return their
safe plan without reading the image. The vision-disabled `503` applies only to
`SCENE_DESCRIPTION`, which genuinely requires the VLM capability.

### Grounded scene response

For `SCENE_DESCRIPTION`, the controller/policy preflight occurs before model
work. The adapter then obtains one ephemeral VLM description and speaks that
description directly through Piper. It does not pass the observation through
the generic text LLM.

P0 provides a general scene description. Existing bounded phrasings such as
`qué tengo en la mano` may request that description, but P0 does not promise a
question-focused visual answer because the raw user utterance is not injected
into the VLM system prompt. A future typed visual task can be designed from
measured need; it is not introduced here.

The VLM prompt is tightened as defense in depth:

- report only visible evidence;
- do not infer identity, gender, relationships, intent, emotion, or hidden
  object contents;
- state uncertainty when evidence is unclear;
- use neutral Spanish phrasing where practical.

Prompt compliance is not treated as an authorization or truth guarantee. P0
still labels the output as current perception, keeps the frame and description
ephemeral, and never promotes either to durable memory.

Vision failure returns a short user-facing Spanish fallback directly. The
existing `PERCEPTION_FAILED` prompt instruction is not reused as spoken text.

## Error handling and degradation

| Failure | Required behavior |
|---|---|
| Intent has no safe deterministic match | Generic conversation only when no protected/ambiguous signal exists |
| Observed ambiguous STT alias | Fixed clarification, no LLM or private audit |
| Protected request from unknown actor | Existing audited non-disclosing denial |
| Invalid/empty streaming protocol before audio | Audible configured fallback, no persistence |
| Stream ends after partial audio | Preserve spoken audio, add fallback, no persistence |
| Robot receives zero-audio completion | Explicit error, never silent success |
| Stream EOF after partial audio but before `done` | Explicit error after preserving already played audio |
| Identity question in P0 | Fixed unknown response, no camera |
| Public biometric-enrollment request | Fixed restricted response, no camera |
| VLM unavailable or empty | Direct audible visual fallback, no second LLM |

## TDD and verification design

Each slice receives its own executable plan, observed RED, minimal GREEN,
focused regression, full gates, and real operator rerun. The plans must not be
implemented as one combined unreviewable change.

### C5 minimum RED matrix

- date: `qué día es hoy`, `qué fecha es hoy`, the observed `Me dice la fecha
  actual.`, `dime la fecha actual`, `en qué fecha estamos`;
- ambiguity: `qué día soy`, `qué vía es hoy`;
- protected precedence: `fecha de nacimiento de mi hija`, `qué edad tiene mi
  hija`, spouse/parent/child variants;
- generic control: `hola, cómo estás`;
- route parity across classic and streaming with no legacy/model call for
  deterministic, ambiguous, or protected outcomes.

### C6 minimum RED matrix

- exact observed hybrid output produces audible fallback and no persistence;
- truncated tag and empty stream produce audible fallback;
- valid fragmented protocol retains sentence streaming;
- failure after one sentence adds fallback without recording a partial turn;
- classic prompt retains exactly its JSON contract and schema;
- streaming prompts, including dynamic markdown profiles, contain exactly one
  streaming contract and no JSON contract markers;
- character parsing no longer requires a universal JSON marker while each
  generation adapter validates/owns its selected contract;
- event order requires at least one audio event before `done`;
- fallback TTS failure yields EOF without `done`, never false success;
- robot treats `done` before audio, EOF without `done` after zero or partial
  audio, duplicate `done`, and out-of-order terminal events as errors;
- normal audio text is logged, while `caplog` proves raw invalid model output
  is absent from operational logs;
- valid flows record server first-audio-ready and robot first-chunk/playback
  timings; invalid flows record `None` plus a bounded reason;
- every emitted WAV remains 16 kHz, mono, signed int16.

### C7 minimum RED matrix

- identity request returns fixed unknown without cue, frame, VLM, LLM, memory,
  or enrollment;
- spoken biometric enrollment returns fixed restricted/unavailable without
  cue, frame, VLM, LLM, memory, or enrollment; update the legacy test that
  currently expects a frame rather than preserving that unsafe expectation;
- scene request returns the exact grounded VLM description and TTS input,
  without generic LLM transformation;
- a red-sphere fixture cannot gain `relajada`, `concentrada`, or a reversed
  object relation;
- VLM failure produces direct audible fallback;
- prompt transport test enforces visible-only and uncertainty rules;
- no-face, no-memory, and image-contract tests remain green; enrollment-route
  tests are deliberately changed to require rejection without a frame;
- HTTP tests cover every cell in the channel behavior matrix, including
  `VISION_ENABLED=false` and direct non-scene `/vision/respond` requests.

### Required real acceptance rerun

Use a disposable database and loopback server.

1. Classic: explicit date, date reformulation, ambiguous alias, protected
   denial, generic greeting, and audible output.
2. Streaming: the same safe cases plus repeated generic greetings; every turn
   must contain audible audio and no `tts=0ms` success.
3. Vision: `quién soy` returns immediately without camera; `qué ves` uses one
   VLM call, no `server.llm` call, preserves visible relationships, and speaks
   the result; VLM failure speaks fallback. The synthetic phrase `aprende mi
   cara, soy PersonaDePrueba` returns the fixed Spanish enrollment rejection
   with `vision_requested=false` and no cue, frame, VLM, LLM, or enrollment.
4. Record literal STT, response text, audio heard, route, model calls, STT/LLM/
   VLM/TTS/total timing, and pass/fail.

P0 is operator-accepted only after the rerun passes on the final commit. Green
automated gates alone remain insufficient.

## Stop conditions

Stop for explicit approval or an ADR if implementation requires:

- a new dependency or model;
- an LLM/embedding/fuzzy authorization classifier;
- a database migration or persistence of learned phrases;
- a public API removal/rename or new streaming transport;
- biometric identity, enrollment, or consent-policy changes;
- durable visual memory, WorldState, tracking, or scene graphs;
- P1 personal/family functionality.
